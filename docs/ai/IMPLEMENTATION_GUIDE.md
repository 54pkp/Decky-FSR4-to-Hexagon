# AI 编程接续指南

适用对象：维护者、开发者，以及接手某个工作包的 AI 编程工具。本文不是执行结果；截至文档建立时，本项目尚无运行时代码或目标设备验收。

[项目首页](../../README.md) · [节点索引](../roadmap/README.md) · [当前进度](../STATUS.md) · [公共合同](../architecture/CONTRACTS.md)

默认协作方式见 [Sol 开发 / Astra 审阅工作流](MULTI_AGENT_WORKFLOW.md)，长期续跑使用 [Goal 提示词](GOAL_PROMPT.md)；已完成的首次 M0 派工记录见[首批工作卡](FIRST_BATCH.md)。本指南保留工程与证据规则；并行时只由唯一 integrator 修改公共状态/合同和操作共享 Git 索引，worker 写自己范围内的产物与报告。

## 1. 从一个工作包开始

任务最小单位是“一个节点中的一个可验收工作包”，例如“为 M1 增加 QNN provider 查询并保存真实错误”，而不是“把全部 FSR4 做出来”。一个工作包应能说明改变了什么行为、依赖什么证据、如何验证、失败后如何恢复。

协调者推荐阅读顺序；worker 按工作卡中指定的小节读取，无需每轮通读：

1. 根目录 `AGENTS.md` 和本次工作卡，首次了解项目时再读一份公开 README。
2. `docs/STATUS.md`，找到实际已完成的代码与测试；不要从文件名或规划勾选推断进展。
3. `docs/architecture/CONTRACTS.md` 的相关小节，确认接口状态与公共术语。
4. 对应 `docs/roadmap/M*.md` 的入口条件和本批交付物。
5. 相关验证报告、上一份交接记录与 ADR；最后按需查归档原始研究及固定版本源码。

`research/` 和 `.research-notes/` 是作者本地忽略目录，新的仓库检出不保证存在。指南中的上游链接才是可独立取得的来源；不要把这些本地目录作为构建或验收的隐式依赖。

## 2. 一次执行的标准流程

### A. 确认现场

- 检查 Git 分支、工作区改动、已有实现、构建入口与测试方式，不覆盖他人未提交内容。
- 确认这是开发主机、交叉编译环境、Odin 3 设备还是游戏环境。记录可访问能力，不假装远程硬件已经连接。
- 阅读依赖节点的报告。如果报告不存在，记为 `not_run`，不要从上游成绩补齐。
- 明确本次唯一主要产物和可验证行为；列出与它直接相关的接口与消费者。

### B. 提出具体实现切片

实施前用[工作包模板](../templates/work-package.md)简要写出：目标、owner、基准、精确文件范围、依赖、算法/接口选择、测试和回滚。分派前先固定最小共享约定，避免多个 worker 独自发明不同 schema。能由已有证据决定的日常实现选择自行推进。只有缺少会影响正确性的输入时才收集信息；不为一般文档、主机测试和可回退修改重复增加批准环节。

若涉及新协议、不同 QNN 版本、图形互操作路径、许可证组合或异步调度，先写一份短 ADR，把选项、决定和验证方式写明。ADR 是工程记录，不自动意味着必须请求额外批准。

### C. 编码与验证

1. 先实现最小正常路径，再覆盖实际可能发生的错误边界。
2. 将 SDK/provider、GPU、IPC 与文件系统依赖放在清晰边界，便于主机测试；替身只能验证控制逻辑。
3. 每批保持可以构建或明确说明尚不成立的构建前提；不要提交满仓库返回成功的空实现。
4. 输出数据、后端类型、时间统计必须来自实际路径。未知值使用 `null` 或 `not_run`，不写成零时延或通过。
5. 按节点验证矩阵执行已有条件下的检查，保存原始日志与精简结论。
6. 检查对共享合同和其它消费者的影响，必要时升级 schema/协议版本。

### D. 留下可接续结果

- 使用[验证报告模板](../templates/validation-report.md)记录证据。
- 使用[交接模板](../templates/handoff.md)写明已改内容、未验证部分、失败假设与下一条具体动作。
- 由 integrator 更新[状态页](../STATUS.md)，分别记录代码、设备和游戏层结果；worker 在自己的交接中提出状态变化，不争写公共文件。
- 一个批次集成和必要检查结束后，用[审阅包](../templates/review-packet.md)交给 Astra。冻结审阅版本，审实际 diff；普通格式/链接改动按工作流由 Sol 检查。
- 检查链接、示例字段和公共 README 是否仍然准确；不要把历史归档当作实时状态页。
- 提交范围只包含任务所需源码、测试与可公开报告。原始资产引用其本地路径、哈希和复现方式，不随意复制进 Git。

## 3. 如何判定“完成”

以下类别用于报告，不能互相替代，也不要求每个工作包都涉及所有类别。

| `evidence_level` | 证明什么 | 不能证明什么 |
| --- | --- | --- |
| `source_review` | 指定版本存在某实现或配置 | 编译通过、运行成功 |
| `build` | 指定工具链可生成产物 | 目标设备能加载或执行 |
| `host_test` | 开发主机上的功能/模拟/CPU 路径行为 | Hexagon 推理、真实游戏兼容 |
| `device_test` | 指定设备/镜像上的真实组件行为 | 完整游戏回写与画质 |
| `game_test` | 指定游戏/API/兼容栈/模型组合的实际行为 | 其它游戏、其它 API 或所有设备都支持 |

单项检查 `gate` 使用 `not_run`、`pass`、`fail`、`blocked`。`pass` 只属于这个检查和它的环境，不是全项目标签。节点实现进度使用 `not_started`、`in_progress`、`blocked`、`complete`，与检查结果分开。

例如：M1 的 provider 枚举在主机测试通过，报告可标 `host_test/pass`；M1 本身仍不能完成，直到目标 HTP 图执行和输出校验通过。M7 的安装事务可在临时目录验证，但真实 Steam/Armada 启动与恢复仍需各自记录。

## 4. 没有硬件时如何继续

可继续：源码审计、协议编解码、尺寸/长度校验、生命周期、模型准备脚本、已具备参考资产的离线重放、配置合并、安装事务、CLI、UI 状态和测试工具。

不能据此宣布：Odin 3 NPU 可用、v79 模型执行成功、游戏帧已回写、功耗收益、输入延迟、Decky 真机体验。

交付“可以在主机验证的部分 + 精确的设备执行清单 + 尚缺的证据”。有需要设备执行的依赖工作时暂停该分支，继续不依赖它的工作包。硬件失败时保留第一现场，不用静默 CPU 回退把问题隐藏。

## 5. 建议工程组织

这些是拟议选型，尚未形成已安装工具链。M0/M1 实施时锁定实际版本，必要时以 ADR 调整。

| 范围 | 建议起点 | 约束 |
| --- | --- | --- |
| 原生服务、QNN、IPC | C++20 + CMake，SDK 边界封装 | 确认目标 glibc/编译器；不从宿主架构推断目标 ABI |
| NGX 代理 | 与加载链匹配的 PE 目标、精确 C ABI | 分开 D3D11/D3D12/Vulkan；异常不穿过 ABI |
| 设备/模型/数据工具 | Python，依赖与输入清单锁定 | 先确认 QAIRT 要求，不统一强制不兼容的 Python 版本 |
| GPU 算法 | 首先复现 EGL/GLES，按证据评估 Vulkan | Android 分配器与导入路径需替换；逐阶段比对 |
| Decky | 跟随验证过的宿主模板，TypeScript/React + Python 后端 | 不固定猜测 Steam 私有接口；后端调用稳定 CLI/服务 API |
| 测试 | 主机单元/集成 + 显式设备/游戏测试入口 | 默认 CI 不需要专有 SDK/游戏/硬件；设备测试不可假通过 |

代码目录与节点对应关系以[公共合同](../architecture/CONTRACTS.md)为准。不要提前生成所有目录和未使用抽象；有首个使用者再创建模块。

## 6. 易导致错误方向的做法

- 只更换一个模型文件，把 XLSR 的 RGB 协议称为 FSR4 后端。
- 根据 `.dll` 名字推断渲染 API，或把 x64/ARM64/ARM64EC 视为可随意替换。
- 为解决性能问题先改成多帧异步，却没有保留 frame ID、history generation 和输入延迟记录。
- 等待尚未提交的 D3D12 工作，或超时后释放仍被 QNN/GPU 使用的内存。
- 用 source/compile/CPU 结果填写 device/game 测试通过。
- 接口异常时返回成功、低分辨率原图或缓存帧，同时保持“NPU 正常”状态。
- 将旧研究的 4 帧流水、静态种子注释或 Android 零拷贝路径未经核对直接移植。
- 替换全部 Steam 启动参数、覆盖其它 mod，或把 Decky 开关直接接到任意 shell。

## 7. 给下一位 AI 的任务提示词

替换尖括号内容后使用；这些文本是任务模板，不是已经执行的命令。

```text
请在 Decky-FSR4-to-Hexagon 仓库实现 <节点编号> 的 <工作包编号/行为>。
先读 AGENTS.md 和 <工作卡路径>，再读卡片指定的 STATUS/合同/节点小节及必要源码。
证据规则不清楚时查 docs/ai/IMPLEMENTATION_GUIDE.md，不默认读取全部研究和聊天历史。

本次环境：<开发主机架构/OS；是否能访问 Odin 3；可用 SDK/模型/游戏>。
本次只交付：<明确行为和文件范围>。
已有依赖证据：<报告路径；没有则明确写没有>。
验收：<主机检查>；<设备/游戏检查，如无设备则列为未运行>。

先检查现有实现与工作区，不覆盖无关修改。按文档拆成最小可验证切片；
接口草案需要变更时记录 ADR 并同步所有消费者，不假定拟议命令已存在。
继续完成已授权的编码与可执行验证。不要用 CPU/mock/cached output 冒充 HTP。
结束时交付代码、验证报告、短 handoff，状态页由 integrator 汇总；列出真实测试命令、退出码、
未运行项目、阻碍和下一步，不虚构设备输出，也不因文档齐全就标记节点完成。
```

每个节点还提供更具体的任务提示词，由协调者裁剪到本批目标后派发。节点中“更新状态”“提交”等收尾责任在并行模式下归 integrator；它们不授权 worker 操作共享 Git 索引。首次移交尽量附带上一份 handoff 与一个验证报告，而不只粘贴整个研究归档。

## 8. 报告命名与变更惯例

拟议报告路径为 `docs/validation/Mx/YYYY-MM-DD-<work-package>.md`，交接为同目录 `YYYY-MM-DD-<work-package>-handoff.md`，ADR 为 `docs/adr/NNNN-<decision>.md`。这些目录在产生真实报告时创建，不用空报告充数。

原始日志放 `artifacts/Mx/<run-id>/` 或其它忽略目录。运行记录同时写 `run_id`、源码提交、环境标识、后端、资产 SHA-256 和时间来源。文件外链暂不可公开时写明获取方式，不创建不存在的下载链接。

公共 README 面向项目访客，不堆放调试日志或内部提示词。新的研究发现写入当前技术报告；归档内容只作历史对照，若发现错误，用勘误链接说明。
